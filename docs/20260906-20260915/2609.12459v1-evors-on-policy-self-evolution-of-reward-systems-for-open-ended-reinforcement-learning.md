## 摘要
开放式强化学习通常依赖基于评分细则的奖励，以应对没有可直接验证答案的任务。然而，策略与奖励系统构成一个动态反馈回路：随着策略优化当前奖励，最初有用的奖励系统可能因 reward hacking 或响应区分度下降而变得不可靠。因此，奖励系统应在训练过程中演化，而非保持固定。现有的动态评分细则方法会调整评价标准，但奖励失效也可能源于评分机制或信号组成。我们提出 EvoRS，一种自演化强化学习框架，它从同策略经验中演化奖励系统，并将其表示为可执行的 Reward-DAG。具体而言，一个智能体式设计器会根据同策略 rollout 和奖励轨迹更新该系统，以维持训练时的可靠性。在写作和角色扮演任务上，EvoRS 在三位评判者下均取得最佳质量，分别比策略高出 \(2.107\) 和 \(4.767\) 分，同时减少 reward hacking 和覆盖失败，并保持奖励信息量。消融实验证实，一个全面的固定奖励系统无法在开放式任务中保持可靠，必须在整个训练过程中演化。

## Abstract
Open-ended reinforcement learning often relies on rubric-based rewards for tasks without directly verifiable answers. Yet the policy and reward system form a dynamic feedback loop: as the policy optimizes the current reward, an initially useful reward system may become unreliable due to reward hacking or reduced response discriminability. The reward system should therefore evolve rather than remain fixed during training. Existing dynamic-rubric methods adapt evaluation criteria, but reward failures can also arise from scoring mechanisms or signal composition. We introduce EvoRS, a self-evolving RL framework that evolves the reward system from on-policy experience, representing it as an executable Reward-DAG. Specifically, an agentic designer updates this system from on-policy rollouts and reward traces to maintain train-time reliability. Across writing and roleplay, EvoRS achieves the best quality under all three judges, outperforming the policy by \(2.107\) and \(4.767\) points, respectively, while reducing reward hacking and coverage failures and preserving reward informativeness. Ablations confirm that a comprehensive fixed reward system cannot remain reliable in open-ended tasks and must evolve throughout training.

## 1. 核心问题与整体含义

- **背景**：强化学习（RL）正被广泛用于训练 LLM 处理开放式任务（写作、角色扮演、办公工作流等）。这类任务没有可直接验证的答案，因而普遍依赖**基于评分细则（rubric）的奖励**，通过 LLM 评判器或生成式奖励模型（GRM）转化为可扩展的训练信号。
- **核心矛盾**：策略与奖励系统构成**动态反馈回路**。策略不断优化当前奖励，而奖励系统本身并未随之变化，导致训练初期有效的奖励在后期失效。
- **三类失效维度**（论文的核心分析框架）：
  - **有效性（Validity）**：出现 reward hacking，策略无需产生预期行为即可拿到高分（如编造权威数据、自证合规）。
  - **覆盖性（Coverage）**：同策略新涌现的响应模式未被当前奖励系统表示，形成覆盖盲区。
  - **信息量（Informativeness）**：奖励信号饱和或同查询组内区分度下降，对优化不再有用。
- **现有方法的不足**：动态 rubric 方法（RLER、OpenRS 等）只调整"评价什么"（criteria），而**评分机制（mechanism）与多信号组合（composition）**通常保持不变。论文指出：同样的评价内容用连续打分、清单核查、缺陷扣分、成对比较等不同机制会产生完全不同的奖励分布与失效模式，因此**只改标准无法解决机制层面的失效**。
- **整体含义**：论文将"奖励可靠性"重新定义为一个**训练期属性（train-time property）**，主张奖励系统必须像策略一样随训练演化，并提出自演化框架 EvoRS。

## 2. 方法论

### 2.1 核心思想

- 把**完整的奖励系统**抽象为可执行的 **Reward-DAG**，使评价标准、打分机制、信号组合三者都在同一统一表示内可编辑。
- 用一个**智能体式设计器（agentic designer）**，基于同策略 rollout 与节点级奖励轨迹做诊断，生成有界候选状态，并通过**匹配重放（matched replay）**比较效果，选出下一状态。
- 关键设计原则：**奖励执行与智能体演化解耦**——设计器只负责提出候选状态，不参与实际奖励计算；两次演化之间当前 DAG 固定不变，保证同一训练阶段内奖励一致、候选间可比。

### 2.2 Reward-DAG 表示

- 状态定义：`D_t = (V_t, E_t, Θ_t)`
  - `V_t`：可执行奖励节点集合
  - `E_t`：节点依赖与执行顺序
  - `Θ_t`：各节点的标准与评分机制，以及节点输出的组合规则
- 节点类型：
  - **Rubric Node（评分节点）**：`h_v = M_{m_v}(x, y; ρ_v, θ_v, J_φ)`，其中 `ρ_v` 可为任务级固定标准，也可由查询级生成器 `G_ψ(x)` 实例化；输出节点级信号。
  - **Composition Operator（组合算子）**：`r_D(x, y) = F_out({h_v : v ∈ Pa(out)}; θ_out)`，负责聚合、归一化、门控或路由，不重新评价响应。
- 实现的节点家族：全局 Rubric 节点、查询级 Rubric 节点、Checklist/Verifier、Deduction/Flaw-Penalty、Composition Operator、Pairwise Comparator。
- 图合法性约束：必须为 pointwise 模式、总节点数 ≤ 10、任一可达路径上评分节点 ≤ 3、无环、从入口可达、聚合算子仅接受上游输入、聚合方法限于 `weighted_sum` / `product`、存在合法终节点。

### 2.3 从同策略经验到候选状态

- 设计器输入：当前状态 `D_t`、同策略经验 `O_t`（rollout + 奖励轨迹）、运行期记忆与动态技能 `K_t`。
- 候选生成：`{e_t^{(j)}}_{j=1..M} = Π_design(D_t, O_t, K_t)`，候选状态 `D̃_{t+1}^{(j)} = e_t^{(j)}(D_t)`，且 `e_t^{(j)} ∈ A(D_t)`（可允许的编辑空间）。
- **类型化编辑操作**：`add_node`、`update_node`（含 `rubric_item_updates` 对稳定 item id 局部修改）、`remove_node`、`set_entry`。所有编辑是事务性的：先克隆、应用、规范化、校验，通过才提交。
- 设计器通过受限工具集工作（诊断工具 + 类型化编辑工具），禁止直接 shell/文件/Python 操作；并受固定技能（fixed skills）与动态技能（dynamic skills）引导。
- 运营化目标只有两个：**On-policy Reward Validity**（合并有效性与覆盖性）与 **Sustainable Reward Informativeness**。

### 2.4 自验证与状态转移

- 用 **匹配重放** 在相同 rollout 案例 `B_t` 上执行当前状态与全部候选状态，使差异归因于奖励系统本身。
- 采样策略：按低分组、高分组、高方差组、随机组四类标准各取 3 个查询组，每组至少 2 条响应。
- 候选进入支持集需同时满足五类条件：
  - `C_exec`：图合法且执行成功率 ≥ 1.0
  - `C_guard`：不新增关键异常维度，默认可靠性维度（区分度、RL 信号、校准、偏差、稳定性、hacking 风险）下降不超过 0.05
  - `C_health`：平均诊断健康分下降不超过 0.15
  - `C_info`：信息量分数 std ≥ 0.02、range ≥ 0.05，最终奖励在匹配案例上非零 std/range
  - `C_review`：模型化对比评审支持分 ≥ 0.55（若启用）
- 若**没有候选带来有支持的改进，则保留当前状态**（no-op），避免奖励目标震荡。
- 选中/被拒/no-op 三类轨迹都存入运行期记忆，并蒸馏为动态技能 `K_{t+1}`。

### 2.5 训练循环（Algorithm 1）

1. 初始化策略 `π_θ0`、初始 DAG `D_0`、记忆与技能 `K_0`；
2. 每步采样查询与分组响应；
3. 若启用查询级 rubric 节点则实例化查询相关标准；
4. 用 `D_t` 打分，记录奖励、节点轨迹、奖励健康摘要；
5. 用 GRPO 式组相对优势更新策略；
6. 非演化步则 `D_{t+1} = D_t`；演化步（默认每 5 步）执行诊断 → 候选生成 → 匹配重放比较 → 状态选择 → 记忆更新。

## 3. 实验设计

### 3.1 任务与数据

- **写作（Writing）**：944 条过滤后的合成开放式写作指令，覆盖 6 个写作领域及受众、格式、长度、风格、语言、交际意图等约束；剔除重复、欠定义、类 benchmark、事实 QA 主导的查询。
- **角色扮演（Roleplay）**：5,000 条来自 MiniMax Role-Play Bench 的查询，保留有明确人设、关系、上下文与对话状态的样本，覆盖中英文场景。

### 3.2 Benchmark 与评价

- **写作**：WritingBench（报告总体分，每响应 5 条查询相关标准，1–10 分后取均值 ×10）。
- **角色扮演**：CoSER，报告 Overall 及 SC、AN、CF、SQ 四个维度。
- **评判模型（三位）**：GPT-5.6-Terra、DeepSeek-V4-Pro、GLM-5.2；采用三者等权平均，并在"共同成功子集"上计算（写作 994/1000，角色扮演 194/200）。
- **奖励可靠性审计指标**：
  - **HR**（Hack Rate）：预设 reward-hacking 模式出现率（写作：编造权威、自证合规、单维度过度优化；角色扮演：装饰性冗长/情绪填充）。
  - **CFR**（Coverage Failure Rate）：预设硬性覆盖失败率（写作：未解决模板残留、非终稿过程痕迹、交付物错配、缺失交付物；角色扮演：必需协议/块失败、OOC/元泄漏、可见上下文矛盾、用户代理权侵犯）。
  - **R-Var / Zero**：同查询组内奖励方差与零区分组比例。
  - 盲评排序审计：480 组，比较奖励排序与独立偏好排序的一致性。

### 3.3 对比方法

- **静态 rubric**：RLAIF（任务级固定 rubric）、RaR（查询级固定 rubric）。
- **动态 rubric**：RLER（用当前策略响应扩充任务 rubric）、OpenRS（成对自适应 rubric）。
- **本方法**：EvoRS，从与 RLAIF 相同的单节点连续奖励系统出发，每 5 步演化一次。
- 所有方法共享同一 GRPO 流程、训练数据、rollout 预算、评估协议，并使用同一本地 **Qwen3.5-27B** GRM。

### 3.4 泛化性与消融设置

- **泛化性**：策略从 Qwen3-4B 扩展到 Qwen3-8B；GRM 从 Qwen3.5-27B 换成 RewardAnything-8B。
- **消融**：
  - 演化策略类：仅标准级适配（限制搜索空间到 rubric criteria）、固定最终 Reward-DAG（从一开始就用 EvoRS 最终发现的完整系统）。
  - 自演化组件类：去掉候选选择、去掉更新拒绝（no-op）、去掉演化记忆/技能。

## 4. 资源与算力

- **硬件**：每次主训练运行使用 **8 张 NVIDIA A800 GPU**。
- **训练规模**：主实验 120 个 GRPO 步；每步 32 个 prompt、每 prompt 4 条 rollout；prompt 长度 4096 token，写作响应 4096 token、角色扮演响应 2048 token。
- **时长与预算**：平均约 **24 小时 wall-clock / 约 192 A800 GPU-hours**（每次主运行）。
- **模型角色**：策略初始化 Qwen3-4B；本地 GRM/查询级 rubric 实例化模型 Qwen3.5-27B；设计器为 Codex SDK + GPT-5.4（每 5 步调用一次）；基准评判为 GPT-5.6-Terra、DeepSeek-V4-Pro、GLM-5.2。专有模型未公开参数量，论文仅报告模型名与角色。
- **运行时开销（写作侧，日志解析）**：
  - RLAIF 511.3s/步、RaR 663.8s/步、RLER 718.4s/步、OpenRS 1037.4s/步；
  - EvoRS 纯训练 753.0s/步，含设计器 801.5s/步，设计器平均更新耗时 242.8s。
- **说明**：离线 benchmark 打分、HR/CFR 审计、盲评标注、多评判评估**不计入** RL 训练 GPU 小时账目；在线奖励打分计入。
